# Backups and restores today, for Lombardi and Ekis

> Research snapshot: 2026-10-02, for [#22](https://github.com/Quick-Release/getquick-site/issues/22)
> on the [phase 4 map (#18)](https://github.com/Quick-Release/getquick-site/issues/18).
> Sources: `@getquick/site` at `45d372d`, `Quick-Release/lombardi` at `2c32080`,
> `Quick-Release/ekis` at `ce258d8` (each repository's `origin/main`), and
> Ploi's and Cloudflare's official documentation. Everything was read-only. No
> API call was made to Ploi or Cloudflare, nothing was restored, and no secret
> or `.env` value was read. Live schedule state (whether a Ploi job exists and
> when it last ran) was **not observed**. Statements about it describe what the
> tooling configures, not what is running.

## Summary

- **Lombardi** has one backup mechanism, the on-demand `pnpm db:backup` /
  `pnpm db:sync` (`gq db backup|sync`). It captures the **database only**, on
  request, into the private releases bucket. Nothing schedules it, and the
  deploy doesn't call it. Media lives in a separate R2 bucket that has no
  second copy. Nothing in the repository backs up the server's `.env`.
- **Ekis** has more tooling but none of it has proven restores. It has Ploi
  scheduled backups (database every 4 h, keep 180; site directory daily,
  keep 14) to R2, a one-off migration archive (site directory plus SQL dump),
  and an older SSH `db sync` that takes no off-site copy. Media is on R2 with
  no second copy, as on Lombardi.
- **Restores.** For either site, nothing on record shows a restore to a
  server, and no procedure for one is written down. The only restore path the
  code exercises is `gq db sync` importing Lombardi's fresh backup into
  **local DDEV**. That proves the dump can be imported, but not that a server
  can be recovered. Ekis's user migration does restore its archive onto a new
  Ploi site. There is no evidence in the repository that it has ever been run.
- **Gate.** Neither site meets the plan's
  [data-recovery guarantees](../plans/getquick-blueprint-rollout.md#deployment-and-data-recovery-guarantees).
  Nothing checks freshness, no backup runs before a data or schema change, no
  migration state is recorded, and no restore has been exercised (see
  [Gaps](#gaps-against-the-plans-data-recovery-guarantees)).

## Inventory

### 1. `gq db backup` / `gq db sync` (`@getquick/site`, used by Lombardi)

| Aspect             | Today                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it captures   | The WordPress database only, from `wp db export - --single-transaction --quick \| gzip`. No uploads, no `.env`, no code. Source: [`src/db/sync.mjs`](../../src/db/sync.mjs) `remoteExportScript`.                                                                                                                                                                                                                                                                                 |
| How it runs        | A Ploi one-off script (`POST /scripts/run`) runs as the site's system user. The script is checked against write-command patterns before it is sent (`assertExportOnly`). It uploads through a 15-minute presigned PUT URL, so the server holds no R2 credentials. Its output gives byte size and SHA-256.                                                                                                                                                                            |
| Where it goes      | `r2://<backups.bucket>/<backups.prefix><database>/<UTC timestamp>.sql.gz` (`backupKey`). For Lombardi, `gq.ops.json` sets `backups.bucket = lombardi-releases` and `prefix = db/`. That is the **same bucket as the release archives** (`releases.bucket`), and the same Cloudflare account as the site's own infrastructure.                                                                                                                                                          |
| Trigger            | Manual only: `pnpm db:backup` / `pnpm db:sync` (Lombardi `package.json`, wrapped in `gq sigillo run staging`). Nothing schedules it. The Lombardi deploy script (`deploy/ploi/admin.sh`) runs `wp core update-db` and deploy extensions **without** taking a backup first.                                                                                                                                                                                                  |
| Retention          | Unbounded and unmanaged. `@getquick/site` sets no lifecycle rule on the bucket, and the releases-bucket token (object read/write, stored in Sigillo `staging`) can overwrite or delete backups. [R2 doesn't implement S3 object versioning](https://developers.cloudflare.com/r2/api/s3/api/). [Bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/) could prevent deletion, but nothing configures them.                                                     |
| Freshness, today   | Nothing reads it. The object key encodes the export time, so freshness means listing `db/<database>/` and taking the newest key or `LastModified`. `src/r2.mjs` has `exists`/`get`/`put`/presign but **no list**, so `gq` can't do this yet.                                                                                                                                                                                                                                  |
| Integrity          | `gq db sync` re-downloads the object and checks its size and SHA-256 against what the server reported. `gq db backup` only trusts the server's report and doesn't re-verify the object.                                                                                                                                                                                                                                                                                         |
| Restore exercised? | **Locally only.** Each `gq db sync` restores the backup it just took into DDEV. It takes a DDEV snapshot first, then imports, search-replaces the URLs, runs `wp core update-db`, and checks the home option, the admin login and GraphQL. That is a working "can this dump be imported" drill, but it is never run against a server. No server restore command or runbook exists. By policy, nothing in `gq` sends a database to a server (Lombardi `AGENTS.md` → Safety). |

Note that Lombardi's live site is a `*.bnq.pt` surface. Its database is named
`lombardi_staging` (`gq.ops.json` `ploi.database`).

### 2. Ploi scheduled backups (Ekis only)

| Aspect             | Today                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tooling            | `pnpm ploi setup backups` (`scripts/ploi/ploi-backups-setup.mjs` → `setupBackups`) creates or updates two Ploi jobs. `pnpm ploi create backup [--database\|--files]` (`ploi-backup-create.mjs`) queues an immediate run. Both arrived in `11a20c4` (2026-07-30). Ekis README → "Automated Ploi backups".                                                                                                                                                                                                                                                                                                                                  |
| What it captures   | **Database job:** the site's Ploi database, every `240` minutes, keeping `180` copies (about 30 days), with `deleteOnFail: true`. **File job:** the whole site directory `/home/<system-user>/<domain>`, daily, keeping `14`. Defaults are in `backupDefaults` and can be overridden with `PLOI_BACKUP_*`. The file archive therefore includes the site-root `.env` and `apps/cms/.env` (production secrets), the code, `vendor/`, and any uploads still on disk. Ploi's file backups can narrow the path and exclude folders ([docs](https://ploi.io/documentation/database/how-do-i-set-up-database-and-file-backups)). The script sets neither. |
| Where it goes      | A Ploi **Custom S3** backup configuration pointed at R2. It has to be created by hand in the Ploi panel, because the API can list these configurations but not create them (README). The bucket and folder are picked interactively (`ploi-backup-target.mjs`) and saved as `PLOI_R2_BUCKET` / `PLOI_R2_PREFIX`. The database job's path is `/<prefix>/database`, and the file job's `local_path` is `/<prefix>/files`. The documented values are the shared bucket `backups-sites` with prefix `ekis.pt` (README; `test-env-plan.mjs` expects `backups-sites`). The bucket is shared across sites and isolated only by prefix.                                   |
| Configuration home | The selected IDs (`PLOI_BACKUP_CONFIGURATION_ID`, `PLOI_DATABASE_BACKUP_ID`, `PLOI_FILE_BACKUP_ID`) go only into the git-ignored root `.env`. They are not in `gq.ops.json`, whose `ploi.serverId`/`siteId` are empty on Ekis `main`. `@getquick/site` has no equivalent yet. The [tooling inventory](getquick-site-tooling-inventory.md) lists it as "shared (later)", with a proposed `ploi.backupConfigurationId`.                                                                                                                                                                                                              |
| Side effect        | `setupBackups` can `PATCH` the Ploi site `.env` (`DB_NAME`/`DB_USER`/`DB_PASSWORD`) when it finds the database binding is stale (`reconcileDatabaseEnvironment`). So "set up backups" is not a read-only operation.                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Freshness, today   | Nothing reads it. Ploi's API returns `last_backup_at`, `status` and `active` on `GET /api/backups/database/{id}` and `GET /api/backups/file/{id}` ([Ploi API inventory](ploi-api.md#get-database-backup)). That is the natural freshness probe. When a job fails, Ploi marks it **Failed** in the panel and emails the server owner, or a configured channel ([docs](https://ploi.io/documentation/database/how-do-i-set-up-database-and-file-backups)). `pnpm ploi create backup` only queues the job and says to "inspect their completion and logs in Ploi".                                                                                                   |
| Restore path       | **Database:** Ploi's panel offers "Restore" from the database's backups window. It overwrites the live database, and Ploi recommends maintenance mode first ([Ploi: restore a database backup](https://ploi.io/documentation/database/how-do-i-restore-a-database-backup)). **Site files:** "Site file backups can't be restored from the panel": download the archive and extract it on the server ([Ploi docs](https://ploi.io/documentation/database/how-do-i-set-up-database-and-file-backups)). Neither restore has an API endpoint in the inventory, a script, or an Ekis runbook.                                                                     |
| Restore exercised? | **No evidence.** The tests use a stateful fake (`3d3f2b7`, `ploi-backup-test-support.mjs`) and cover only the configuration, not a backup's content or restorability. Whether the jobs exist and are running on the live account was not checked.                                                                                                                                                                                                                                                                                                                                                                                          |

Lombardi has no Ploi scheduled backup configured from its repository. Neither
the code nor `gq.ops.json` mentions one. If one exists, it was made by hand in
the panel, and this snapshot didn't observe it.

### 5. Ekis `pnpm db sync` (legacy, for completeness)

`scripts/db-sync.mjs` exports the live database over SSH through an
exact-string allowlisted read-only command
(`wp db export - --single-transaction --skip-lock-tables`). It takes a local
DDEV snapshot (`before-live-sync-…`) and imports the export into DDEV. **No
copy is kept off the server**: the dump goes straight to the developer's
machine. The tooling inventory marks it obsolete in favour of `gq db sync`, but
keeps its exact-string allowlist as a hardening idea.

and the phase 4/5 gate rows. They are listed for whoever decides #31's gate.
They don't decide it.

| Guarantee                                                                    | Lombardi                                                                                                                                         | Ekis                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Verify backup freshness before data/schema changes**                       | Missing. The deploy runs `wp core update-db` and extensions with no backup and no freshness check. `gq` can't list R2 objects to read freshness. | Missing. Schedules exist (if set up), and `last_backup_at` is available from the Ploi API, but nothing reads it, and the deploy has no gate.                                                                                               |

Other gaps that cut across both sites:

- **Media has no backup at all** on either site. R2 has no versioning,
  WordPress holds delete rights, and nothing replicates or locks the bucket.
- **Neither site backs up `.env` on purpose.** Lombardi's isn't backed up at
  all. Ekis's ends up in Ploi file archives and migration archives as a side
  effect.
- **Retention is unmanaged** on every R2 destination `gq` controls (no
  lifecycle rules). The only bounded retention is Ploi's keep-N.
- **The two sites use different mechanisms.** Lombardi uses a `gq`-driven
  on-demand export to its own bucket. Ekis uses Ploi-managed schedules to a
  shared bucket, configured through `.env` rather than `gq.ops.json`. A shared
  recovery gate needs one shape. The tooling inventory already plans to move
  Ploi scheduled backups into `@getquick/site` as `gq.ops.json` `backups` plus
  `ploi.backupConfigurationId`.
- **Every copy sits in the same Cloudflare account**
  (`8f38791a…`) as the site's own infrastructure. There is no off-account or
  off-provider copy.

## How freshness could be read (without mutating anything)

- **`gq db backup` objects.** List `r2://<backups.bucket>/<prefix><database>/`
  with S3 `ListObjectsV2` and take the newest key's timestamp or
  `LastModified`. This needs a list method in `src/r2.mjs` and a read-only
  token.
- **Ploi scheduled jobs.** `GET /api/backups/database/{id}` and
  `GET /api/backups/file/{id}` return `last_backup_at`, `status` and `active`.
  The IDs are the ones `pnpm ploi setup backups` saves.
- **Integrity alongside freshness.** For `gq` backups, compare the object's
  size with the server-reported SHA-256 (recorded only in command output
  today, not stored). For Ploi backups there is no checksum in the API
  response. A test import into a disposable database is the only real check.
