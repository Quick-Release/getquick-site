Keep the accepted architecture
Bedrock CMS + WPGraphQL → Astro SSR → Cloudflare Workers. This is not a proposal to replace WordPress or the hosting implementation.
Keep site ownership
App skeletons are create-once, then site-owned. Shared runtime fixes belong in versioned packages, not forced overwrites (ADRs 0001 / 0002).
Choose the support promise
The current implementation assumes GETQUICK theme/plugins, not arbitrary WordPress. Archives, search, previews and plugin-specific behaviour need an explicit support decision.

Problem: CMS outages, GraphQL errors and genuinely missing content collapse into the same result; pages and layout separately orchestrate CMS requests.

Solution: Deepen CMS delivery so transport policy, required capabilities, fallbacks and failure meaning live together, preserving the intentional no-CMS development state without hiding production failures.

  • Locality: one failure policy
  • Leverage: content and chrome together
  • Tests distinguish missing from unavailable
Evidence: getEntryByUri returns null on HTTP 503; the route turns it into 404. Homepage access to absent designTokens also discards otherwise valid content. GraphQL errors are always thrown; the block retry only handles HTTP 5xx and only for entries, not home. Existing tests explicitly lock timeout → null, so that contract would need an intentional change.
Do not silently treat required GETQUICK schema fields as optional. First decide which capabilities must fail readiness and which may degrade. Start with request-scoped reuse/concurrency; cross-request caching needs freshness requirements and measurements.
Deletion test: merely extracting fetch adds indirection; concentrating failure and capability decisions removes repeated knowledge from routes, layout and later readiness checks.

Problem: adding a Video Hero changes unrelated block rendering, while required WordPress layout knowledge is spread across HTML reconstruction, CSS, preset generation and page branches.

Solution: establish one supported block-presentation implementation that preserves server-rendered output, limits custom reconstruction, and keeps required styles with the behaviour they implement.

  • Locality: HTML and CSS agree
  • Leverage: same blocks on every page
  • Tests cover mixed block trees
Evidence: a block with empty htmlContent and complete dynamicContent renders as an empty string. The four-name rendered-children list is a heuristic, not a general reconstruction rule. Presets export only colors/spacing; typography, gradients and global layout settings are outside the current implementation. Existing tests cover Video Hero, URL safety and constrained GETQUICK containers, not full CMS/browser parity.
Do not rebuild all Gutenberg blocks in TypeScript or merge the CSS into one giant file. Internal seams can stay. Define a supported block set and test real CMS fixtures, especially mixed dynamic content, containers and hero pages.
Deletion test: the helpers earn their keep; deleting them moves layout complexity back into callers. Deepen their shared ownership and test surface, not their file count.

Problem: the Frontend drops nested menu children, splits site identity, and normalizes CMS-origin menu links but not identical links saved in body content.

Solution: deepen the existing document/navigation slice and localize public-link policy across navigation and content; separately decide whether the Blueprint also promises reading modes and archives.

Confirmed gaps: buildMenuTree has children and a test, while Layout.astro renders roots only. Saved absolute CMS-origin body anchors pass through unchanged and can lead anonymous readers to the CMS's intentional 404; whether the editor creates those links requires CMS verification. Logo fallback/header/title suffix use the generated name. The menu request caps at 100 without pagination. Language and date locale are fixed to English.
Archives, search, custom post types, draft previews and SEO-plugin support are scope decisions, not proven regressions. Deletion test: deleting a pass-through route helper gains nothing; centralizing route/identity knowledge prevents the same editorial decisions being reimplemented in home, entries, navigation and metadata.

Problem: WordPress delivery/rendering fixes in the Blueprint reach new sites only; every existing site keeps its own implementation.

Solution: after settling the delivery/presentation contracts, move genuinely common behaviour and required styles into versioned shared modules while keeping the App skeleton thin and site-owned.

  • Leverage: one fix across sites
  • Locality: compatibility tested together
  • Tests protect dependency upgrades
ADR alignment, not a conflict: ADR 0001 and the rollout plan already call for shared renderer/block-contract packages. Reclassifying whole Astro apps as fully generated would contradict ADR 0002; this recommendation explicitly avoids that.
Deletion test: moving unchanged files to npm is distribution work, not depth by itself. The gain comes when callers no longer need CMS transport, block semantics and required-style knowledge. Extract proven common behaviour; do not package client branding or arbitrary future customizations.

Problem: Blueprint checks validate generation and CLI behaviour but do not execute the embedded Frontend tests or prove rendered pages match a supported CMS.

Solution: deepen generated-site acceptance into a reusable scenario module, with fast deterministic route checks plus a separate real-CMS compatibility gate and explicit readiness diagnostics.

  • Locality: setup and proof together
  • Leverage: every Blueprint change checked
  • Tests cross real rendering seams
Evidence: root checks ran 355 Node tests; all passed. The separate 22 Frontend library tests also passed in an isolated TypeScript harness. The first direct attempt could not resolve astro/tsconfigs/strict, because the Blueprint repo does not install the generated app's Astro dependency. The CMS example test asserts true; the existing hosted smoke verifies titles, not a published block-rich page. The Frontend's build script runs only astro check; deployment relies on Alchemy for the actual artifact build.
Readiness gap: local startup reports ready after DDEV/environment wiring, without WordPress installation or manifest-plugin/theme activation. Hosted activation happens only on a deploy after browser installation. An explicit post-install preparation/check path should distinguish runtime startup from a CMS ready for the Frontend; do not run production migration extensions locally.
The documented phase-2 smoke deployment passed; this is stronger recurring coverage, not a claim deployment is broken. gq new must remain offline and secret-free. Install/activate/seed only in explicit post-generation or disposable-test steps; never silently reset an existing site's CMS.
Deletion test: isolated fixture helpers alone are shallow. A module that owns generation, scenario setup, runtime execution and observable assertions concentrates the complexity now scattered across string tests, startup reporting and manual smoke steps.

Top recommendation

Start with CMS delivery, protected by rendered-site tests.

Stop turning temporary CMS failures into 404s before extending WordPress support; then deepen block presentation and extract the proven runtime without overwriting site-owned apps.

Explore candidate 1 →

Selected direction: durable published-content delivery

Normal serving Read cached published content. WordPress publication events refresh it.
Outage Keep last-known-good content until the CMS recovers; no age limit. Never replace a good copy with failed or empty refresh output.
Withdrawal Accepted unpublish/delete events stop serving that content immediately. An unreachable CMS plus a lost event cannot reveal a withdrawal.
Reconciliation Periodic checks target a five-minute missed-event recovery window when the CMS is healthy.
Refresh coverage Published pages/posts and shared menus, logo, identity and design presets.
Editor experience Publishing remains available; refresh failures retry and report the delay.
Media Require independent WordPress upload hosting through the existing R2 media path.
Feasibility: the inspected Frontend declares no content-storage binding or event receiver. CMS event authentication, retry execution and secret plumbing need additions; private GETQUICK plugin capabilities remain unverified. Production disables WP-Cron, so retries must not assume traffic-driven scheduling. Existing CI signing/delivery patterns offer implementation precedent, not an existing publication mechanism.

This choice expands the candidate from error handling into an event-refreshed published-content module. Cache/storage design, consistency, compatibility and rollout still need design work. New-site support must preserve offline generation and site-owned apps.
