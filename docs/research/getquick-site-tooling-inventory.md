# GETQUICK site tooling inventory

The recommended classification of Lombardi's and Ekis's tooling, for the
phase 1 extraction tickets of the
[blueprint rollout](../plans/getquick-blueprint-rollout.md) ([Quick-Release/lombardi#7](https://github.com/Quick-Release/lombardi/issues/7),
parent spec [Quick-Release/lombardi#6](https://github.com/Quick-Release/lombardi/issues/6)) to follow. Researched on 2026-09-30 against Lombardi
`f9d710b` and Ekis `origin/main` `ce258d8`. No Ekis file was changed. Moved
here from Lombardi on 2026-10-01; "the spec" is Lombardi's phase 1 spec, and
provider IDs found in the code are omitted.

Every Lombardi root script and tooling module and every Ekis tooling script
appears once, with one of three classifications:

- **shared**: any GETQUICK site would run it with only `gq.ops.json` (or
  release config: the site's `shop-devtools.config.mjs`) differences. It
  moves into `@getquick/site`.
- **site-owned**: it encodes this site's content, apps, or choices. It stays
  in the site.
- **obsolete**: superseded by another copy or dead. Nothing moves.

For Ekis, **shared (later)** marks a capability that is fuller than
Lombardi's. It is recorded as a later addition to the package (phase 4), not
phase 1 work. Phase 1 extracts Lombardi's version of everything.

## Edge cases

The classifications the issue asked to settle. They are recommendations for
the extraction tickets; where one departs from the spec, it says so.

| Question                                   | Classification                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Composer wrapper (`cms-composer.mjs`)      | **Shared.** Nothing in it is Lombardi's. It encodes the GETQUICK stack: registry login only on the host, DDEV's PHP when it is running, relinking around dependency changes. Ekis requires the same registry packages and has the same `lint`/`lint:fix`/`test` Composer scripts. Shared `db:sync` calls its `composerInstall`, so keeping the wrapper in the site would force a site-hook seam, which is a redesign. The CMS check list stays site-owned: it lives in `apps/cms/composer.json` and `shop-devtools.config.mjs`, not in the wrapper. This departs from the spec's example that lists "Composer wrappers" as site-owned (user story 24), which the spec allows "unless the inventory shows them generic". |
| Local Design source override               | **Shared, as is.** It targets `getquick-design`, a registry plugin that Ekis also installs (`^0.2.7`). Its opt-in is a per-developer, gitignored `.local-plugins/config.json`, so it holds no site value. Shared `cms:dev` (DDEV start and its lock) and `db:sync` call it. The generated DDEV hook path must become a `gq` invocation. Generalising it to other registry plugins is a later addition.                                                                                                                                                                                                                                                                                                                  |
| `verify` check list                        | Runner **shared**. The list stays **site-owned** in `shop-devtools.config.mjs` `checks`, as today. In phase 1 the runner keeps its current rule that a check needs PHP when `cmd === "composer"`, and it skips those checks locally when there is no Composer or no `apps/cms/vendor`. [Quick-Release/lombardi#16](https://github.com/Quick-Release/lombardi/issues/16) brought the declared field forward: a check may list `requires` (`php`, `ddev`), and Lombardi declares `php` on its Composer checks.                                                                                                                                                                                                            |
| `doctor` check list                        | Runner and generic checks **shared** (Node, pnpm pin, git, Composer vendor, Artifacts remote, `.env` presence, Sigillo, DDEV). It also adds the installed `@getquick/site` version. The site supplies its inputs: the required app files (Lombardi requires `astro.config.mjs`; Ekis's frontend is TanStack Start and has none), the Node minimum (from `package.json` `engines.node`), and the DDEV project name (from `apps/cms/.ddev/config.yaml` `name`).                                                                                                                                                                                                                                                           |
| Ekis `command` / `test env` / `db` routers | **Obsolete.** They are single-subcommand dispatchers (`db sync`, `test env`) and a static command list (`command list`), all replaced by `gq`'s own subcommands and help. The audit behind `test env` (`test-env.mjs`) is **shared (later)**: a remote extension of `doctor` that checks Ploi and Cloudflare credentials, rewritten to read `gq.ops.json` and never write `.env`.                                                                                                                                                                                                                                                                                                                                       |
| `post-deploy` smoke tests                  | **Not phase 1.** Lombardi has none. `gq-ops`'s `test post-deploy` only shells out to a site's `pnpm gq` script, which Lombardi doesn't have, so it is obsolete. Ekis's `post-deploy.mjs` splits two ways. Its runner is **shared (later)**: retries, same-origin redirects, content-type checks, plus the generic endpoints CMS `/wp-json/`, the `getquick-config` and `getquick-design` REST routes, and the frontend home. Its checks for docs, storefront, cart and customer-auth are site-owned. When it is built, the rollout plan's rule that an HTTP 200 alone is insufficient applies: consider `/wp/graphql` and a deployed-version check.                                                                     |
| Ekis's fuller capabilities                 | All **shared (later)**: the original `shop-devtools` extras, Ploi scheduled backups, system-user migration, Cloudflare token rotation and validation, revision verification in the CI Worker, and smaller pieces. See [Later additions](#later-additions-from-ekis).                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| CI Worker and Alchemy config               | **Site-owned in phase 1.** `infra/ci` and `infra/` are per-site deployables with their own `package.json`, and `AGENTS.md` gives `infra/` ownership of Alchemy config. They are phase 2 managed-file candidates. Their hardcoded values are still [listed](#site-owned-files-that-phase-2-will-template) so phase 2 can generate them.                                                                                                                                                                                                                                                                                                                                                                                  |
